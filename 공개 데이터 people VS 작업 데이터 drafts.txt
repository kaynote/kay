처음부터 한꺼번에 뜯어고치지 않고, 현재 잘 돌아가는 302개 게시물과 댓글 시스템을 보존하면서 단계별로 진행하는 게 안전.

kay/

├─ people.js        ← 건드리지 않음

2단계 — 관리자 페이지를 별도로 만든다.

GitHub 저장소에 다음 세 파일을 새로 만든다.

admin.html
admin.js
admin.css
처음에는 아주 단순하게 만들 거야.

관리자가

/kay/admin.html
로 들어갔을 때만 관리자 화면이 나타나게 한다.

일반 사용자가 들어오면:

관리자 권한이 없습니다.
라고 표시한다.

-------------------------------------------------

3단계 — 관리자 UID 확인

현재 네 코드에 있는:

const ADMIN_UID = "8OEfoiQCXDdIodCjbyXP0ZNints1";
이것은 그대로 사용할 수 있어.

중요한 것은:

이 UID를 숨기는 것이 목적이 아니다.

일반 사용자가 알아도 그 UID 자체로 로그인할 수는 없다.

관리자 판별은:

currentUser.uid === ADMIN_UID
으로 한다.

-------------------------------------------------

4단계 — admin.html부터 만든다.

일단 아래 정도의 아주 단순한 관리자 페이지부터 만든다.

<!DOCTYPE html>
<html lang="ko">

    <link rel="stylesheet" href="admin.css">

<body>

    <div id="adminApp">

        <h1>Kay 기록 보관소 관리자</h1>

        <div id="loginStatus">
            확인 중...
        </div>

            <h2>관리자 모드</h2>

</html>

6단계 — admin.js에서 Firebase 로그인 상태 확인

여기가 중요하다.

현재 사이트에서 사용하고 있는 Firebase 인증 방식을 그대로 이용해야 한다.

그래서 여기서 바로 코드를 새로 짜기보다 네 firebase.js에 현재 어떤 Auth 코드가 들어 있는지 확인하고 맞추는 게 안전하다.

개념적으로는:

const ADMIN_UID = "8OEfoQCXDdIodCjbyXP0ZNints1";

onAuthStateChanged(auth, (user) => {

    if (!user) {
        // 로그인하지 않은 상태
        return;
    }

    if (user.uid === ADMIN_UID) {
        // 관리자
    } else {
        // 일반 사용자
    }

});

이런 구조가 된다.

7단계 — 여기서 첫 번째 테스트
여기서는 Draft도 만들지 않는다.

먼저 이것만 테스트한다.

관리자 계정으로 접속
/kay/admin.html
→

관리자 모드
관리자로 로그인되어 있습니다.
가 나오는지 확인.

일반 사용자 계정으로 접속
→

접근 불가
관리자 계정만 사용할 수 있습니다.
가 나오는지 확인.

로그아웃 상태
→ 관리자 화면에 들어갈 수 없어야 한다.

8단계 — 이 단계가 성공하면 다음 단계
여기까지 성공했다고 해서 아직 기존 사이트에는 아무 변화가 없다.

즉:

기존 사용자 사이트
       ↓
       그대로

기존 302개 게시물
       ↓
       그대로

좋아요
       ↓
       그대로

댓글
       ↓

       ↓

조회수
       ↓

그리고 새로 생긴 것은:

admin.html
admin.js
admin.css
뿐이다.

이 상태를 먼저 완성하는 것이 중요하다.

-------------------------------------------------

9단계 — 그다음 Draft 구조를 만든다.

관리자 인증이 확인되면 Firebase에 별도의 drafts 영역을 만든다.

현재 공개 데이터와 분리한다.

예를 들어:

Firestore

people
 ├─ 001
 ├─ 002
 ├─ 003
 └─ ...

drafts
 ├─ 001
 ├─ 002
 ├─ 003
 └─ ...
여기서 아주 중요한 규칙:

people
일반 사용자에게 보여주는 현재 공개본

drafts
관리자가 수정하는 작업본

이다.

-------------------------------------------------

10단계 — 예를 들어 001번 게시물을 수정한다고 하자.

현재:

people/001

name: ...
ko: ...
displayName: ...
note: ...
image: ...
가 있다고 하면 관리자가 관리자 페이지에서

001번
설명 수정

"기존 설명"
        ↓
"새로운 설명"
을 한다.

그런데 바로 people/001을 수정하지 않는다.

대신:

drafts/001
에 저장한다.

즉:

공개본
people/001
     │
     │ 복사
     ▼
작업본
drafts/001
     │
     │ 관리자 수정
     ▼
수정된 Draft

-------------------------------------------------

11단계 — 그러면 일반 사용자는 전혀 모른다.

관리자가:

drafts/001
에서 10번 수정해도 일반 사용자가 보는 것은:

people/001
이다.

따라서:

관리자:
"사진 바꿔야지"

일반 사용자:
"아무 변화 없음"
이 된다.

관리자가:

"이제 완성됐다"
라고 판단했을 때만 Publish한다.

-------------------------------------------------

12단계 — Publish

관리자 화면에:

[저장]

[미리보기]

[Publish]
같은 버튼을 만든다.

Publish를 누르면:

drafts/001
      ↓
      ↓ Publish
      ↓
people/001
으로 반영한다.

그러면 그때부터 일반 사용자에게 새 내용이 보인다.

-------------------------------------------------

13단계 — 기존 댓글/좋아요/조회수는 건드리지 않는다.

이 부분이 특히 중요해.

현재 구조가 대략:

people/{게시물}

 ├─ views
 ├─ likes
 └─ comments
       └─ replies
라면 Draft를 만들면서 이것들을 복사해서 관리하면 안 된다.

예를 들어:

drafts/001
에는

사진
제목
설명
기타 게시물 정보
같은 콘텐츠만 들어간다.

반면:

people/001/views
people/001/likes
people/001/comments
는 기존 그대로 유지한다.

그래야 관리자가 설명을 수정했다고 해서 좋아요/댓글이 사라지는 문제가 생기지 않는다.

-------------------------------------------------

14단계 — 더 안전하게 하려면 Publish 이전에 백업.

최종적으로는 이것도 넣는 게 좋다.

people/001
     │
     ├── 현재 공개본
     │
     │ Publish
     ▼
backup/001
     │
     └── Publish 직전 공개본
그래서 실수로:

Publish
했더라도 이전 버전으로 되돌릴 수 있게 한다.

즉 최종적으로:

Draft
 ↓
Preview
 ↓
Publish
 ↓
Public
 ↓
Backup
구조를 만들 수 있다.

-------------------------------------------------

15단계 — 그런데 지금 가장 중요한 문제 하나.

현재 사이트는 people.js가 302개 게시물의 정적 데이터 역할을 하고 있기 때문에,

단순히 Firestore에

drafts
를 만들어 놓는다고 해서 기존 사이트가 자동으로 drafts → people.js로 바뀌지는 않는다.

이 부분은 나중에 정확하게 연결해야 한다.

그래서 처음부터 people.js를 없애거나 기존 index.html을 Firestore 기반으로 전부 뜯어고치면 안 된다.

우리는 다음 순서로 갈 거야.

① 관리자 페이지 생성
       ↓
② 관리자 UID 인증
       ↓
③ 관리자 페이지 테스트
       ↓
④ Draft 데이터 구조 생성
       ↓
⑤ 관리자에서 게시물 하나 불러오기
       ↓
⑥ Draft 수정
       ↓
⑦ Preview
       ↓
⑧ Publish 구조 결정
       ↓
⑨ Publish를 기존 공개 시스템과 연결
       ↓
⑩ 마지막에 필요하면 자동 백업/롤백
